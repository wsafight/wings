# ADR-0002：语言前端与 AOT 后端

- 日期：2026-11-12
- 状态：已采纳（设计）；消息语法部分由 [ADR-0007](0007-message-handlers-and-state.md) 替代，单前端与 AOT 决定不变

## 背景

资源检查、抢占和精确根需要覆盖全部受管业务代码。普通 Rust 库或 proc-macro 无法控制依赖内部的循环、寄存器分配与栈布局。直接自研机器码后端又会增加双平台维护成本。

## 决定

- 只提供 `wings-lang` 前端，借鉴 Elixir 的消息与模式匹配写法，不承诺 Elixir 语法或生态兼容。
- 编译流程为语法分析、类型化 HIR、受管 IR、Cranelift AOT，再链接组装目标平台产物。受管 IR 明确表示 safepoint、根、栈限额和受管调用。
- 使用独立的 `wings-compile` 工具。VM 装载匹配目标与版本的受控产物，不在首版内置 JIT。
- 首版静态加载；热更新留到 M5，只在 handler 返回后的 Idle 边界迁移状态，旧代码有引用时不能卸载，不修改活跃返回地址。
- 普通 Rust 只能作为经过审计、有预算的可信原生内建，不提供受限 Rust 子集前端或任意库透明导入。

## 替代方案

- Rust 子集前端：检查覆盖和 ABI 很难仅靠宏保证，不采用。
- 字节码解释器或 JIT：保留为未来比较对象，首版不同时维护多种执行方式。
- 自研后端或先上更重的优化后端：先验证现成 AOT 路线，后端更换由端到端数据决定。

## 影响

团队需要承担新语言与工具链成本，AOT 本身并不保证优于 BEAM。产物格式、最终链接、平台签名与装载策略仍须在 M0 原型中确认；采用本决策不代表这些工作已经完成。

## 重审条件

后端无法满足精确根、切换恢复或目标平台要求，或生成代码已成为实测主要瓶颈时，提出新的后端决策。
