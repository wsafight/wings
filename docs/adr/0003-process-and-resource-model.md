# ADR-0003：微进程与资源模型

- 日期：2026-11-12
- 状态：已采纳（设计）

## 背景

只给每个进程设置堆上限，无法限制 mailbox、spawn、计时器或外部 I/O 的增长。消息和恢复的时机也必须与状态提交一致，否则很难判断失败后哪些副作用已经发生。

## 决定

- 微进程拥有逻辑独立的 arena 与业务状态，不共享可变业务数据。共享分配池不等于每个进程独立映射，也不提供 OS 级安全隔离。
- handler 采用返回式模型，正常返回时提交新状态和自动回复；`send`、`request`、`spawn` 的副作用在调用点生效，后续失败不会撤回。
- actor 内只做异步交互，首版不提供函数内部阻塞的 `receive`、`await` 或同步 `call`。
- 可增长资源分配前经过微进程、租户、VM 实例三级准入。资源转移、失败回滚和退出清理保持额度守恒，mailbox 满时显式报错。
- Idle 才释放执行上下文并可能冬眠，被抢占的 handler 仍保留活栈。冬眠默认关闭。
- 受管业务错误可结束单个微进程；编译器、VM 和可信原生内存错误仍可能结束整个 VM。不可信原生扩展留给后续 OS 子进程池。

## 替代方案

- actor 内隐式阻塞等待：需要另外设计续体和取消模型，首版不提供。
- handler 返回后一次性提交所有副作用：会改变普通消息模型，首版不采用事务式 effects 列表。
- 每个微进程使用 OS 进程隔离：资源与调度成本不同，不作为当前轻量进程实现。

## 影响

业务需要显式处理发送失败、异步回复、超时和幂等重试。监督负责恢复，不提供持久投递、exactly-once 或额外的内存隔离。

## 重审条件

引入函数内部等待、共享对象所有权转移或新的准入缓存行为时，先说明对状态、消息顺序、额度和失败恢复的影响，再决定是否改变契约。
