# ADR-0006：Workspace 边界与 LSP

- 日期：2026-11-12
- 状态：已采纳（设计）

## 背景

编译器需要完整代码生成能力，LSP 需要快速处理不完整、未保存的源码，VM 则只需要装载产物。如果都放进一个包，编辑器查询会被迫依赖后端与执行引擎；如果各写一套前端，诊断和语义又容易分叉。

## 决定

- 共享 `wings-source`、`wings-syntax`、`wings-sema`，统一源码位置、容错语法树、诊断、符号和类型分析。
- 编译路径单独设置 `wings-ir`、`wings-codegen` 和 `wings-compile`，区分业务 HIR、受管执行 IR、机器码生成和编译驱动。
- `wings-vm` 与编译器仅共用 `wings-abi` 和 `wings-artifact`，不相互依赖实现。ABI 布局与元数据编码显式定义，不把 Rust 对象布局当稳定格式。
- 提供独立的 `wings-lsp` 包与 stdio 服务器，仅依赖共享语言分析库，不依赖 Cranelift、VM、汇编切换桩，也不运行用户程序完成查询。
- LSP 首批包含文档同步、诊断、跳转、悬停和基础补全；按版本处理快照、取消与过时结果，协议位置编码在 LSP 层转换。
- 调度、GC、mailbox、资源与平台实现先作为 VM 内部模块。只有出现实际复用或构建隔离需求时再拆包，不为每个模块预建 crate。

## 替代方案

- 单体 crate：最初目录少，但会使 LSP 和 VM 带上不需要的依赖，不采用。
- LSP 调用编译命令解析输出：难以处理未保存输入、查询取消与符号查询，不作为普通编辑请求路径。
- 调度、GC、分配器和平台各自独立 crate：当前边界尚未验证，过早公开接口，不采用。

## 影响

需要维护一个无环 workspace，以及可查询、可恢复的前端。公共查询接口和夹具可减少编译器与编辑器差异，但不会自动带来增量性能，仍需实际测量。外部 LSP/增量框架及具体版本尚未选择。

## 重审条件

有实际复用、接口稳定性、构建时间或编辑响应数据表明边界不合适时，可以合并或细分包；需要改变依赖方向时同步修改 crate 设计和依赖验收。
