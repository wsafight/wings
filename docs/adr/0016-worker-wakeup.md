# ADR-0016：单 waiter 的 OS 通知原语

- 日期：2026-11-12
- 状态：已采纳（M0 实现契约）；平台实现须分别运行 CI
- 相关决定：[首要平台](0005-platforms-and-benchmarks.md)、[受管抢占](0004-safepoints-and-gc.md)

## 背景与决定

空闲 worker 需要可唤醒的 OS 等待，不能用忙轮询或通知次数代替队列内容。先验证平台描述符、超时和通知生命周期，再接入进程队列与 I/O。

- `WorkerParker` 独占等待端，`wait(&mut self, Duration)` 返回通知提示或超时；同一对象不能被多个线程同时等待。允许在没有等待时按值移交线程，不提供 Clone/Sync。
- `WorkerNotifier` 可克隆、跨线程通知，通过共享所有权保持底层描述符有效。等待端销毁后，已有 notifier 可继续安全调用，直到最后一个引用消失才关闭资源；没有等待者不等于对不存在的进程投递成功。
- Linux 使用 `epoll` + 非阻塞 `eventfd`，macOS 使用 `kqueue` 的 `EVFILT_USER` + `EV_CLEAR`。描述符设置 close-on-exec；创建或注册失败按所有权回收，返回 I/O 错误。
- Linux 的 close-on-exec 随创建原子设置；macOS 的 kqueue 创建后再以 fcntl 设置，存在与并发 fork/exec 的窗口。当前不提供并发派生子进程协议，未来接入时必须统一串行化描述符创建与子进程派生或采用经验证的平台机制，不能声称已解决该竞争。
- 通知是可合并的重查提示，不承载消息数或业务顺序。先通知后等待也应可观察；Linux 计数器饱和视为已经有通知。等待端消费当前可见通知，通知与消费竞争允许合并，但必须在返回后重查外部队列。
- 调用者先检查队列，无工作才等待；通知发送方必须先发布队列内容，再通知。等待返回后重新检查队列及终止标志，不从一次 `true` 推断有多少项。原语不负责发布业务内存，也不保证多个消费者公平性。
- 零超时只轮询；非零超时采用单调时钟截止时间，系统等待分辨率不足时向上舍入。被信号打断后仅等待剩余时间，不重新使用完整超时；无法表示的截止时间明确拒绝，不溢出或变成无限等待。

## 验证

在有 CPU/墙钟限制且禁 core dump 的子进程内，以 debug/release 覆盖无通知超时、零超时、提前通知、合并通知、跨线程唤醒、多个生产者、反复通知/等待交错、等待端移交以及任一 handle 先释放时的生命周期。循环与线程数有固定上限，不做宿主 FD 耗尽或信号风暴。macOS AArch64 与 Linux x86-64 必须独立通过；本机通过不能证明另一后端正确。

## 影响与后续

这只是 OS 唤醒，不会中断计算，不引入计时线程、I/O 适配器或 worker 调度器。受管代码仍通过原子轮询让出。不改变 ABI 或语言，也未将 FD/控制块接入三级账户；集成时须先预留固定 worker 资源，并验证队列发布与等待竞争协议。精确根、栈限额和业务负载冻结仍为 M0 待办。

替代方案是轮询加 sleep 或 condition variable：前者增加空闲 CPU 或唤醒延迟，后者不能直接复用既定 OS I/O 等待路径。后续若增加多个事件源、FD 取消或工作窃取，需要独立扩展注册和独占消费协议，不把此单通知源接口当作完整 reactor。
