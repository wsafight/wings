# ADR-0082：macOS TCP 分段限制与运行期间的缓冲检查

- 日期：2026-11-14
- 状态：已采纳（受限 TCP 资源边界修正）
- 部分替代：[ADR-0048](0048-bounded-loopback-service.md) 仅设置并读取一次 socket 缓冲便认为后续仍受限的安排。
- 沿用：原 16 KiB 收发缓冲设置、64 KiB 单缓冲验收上限、全部资源额度、连接/帧数和 I/O/请求/业务时限；不修改 ABI v15 或语言。

## 问题与证据

ADR-0081 验证中原 TCP 场景两次出现关闭或计数错误。独立受限探针在 macOS 26.6.2 / Darwin 25.6.0 上观察到设置 SO_RCVBUF=16384 后读取到 277696；SO_RCVBUF 并非持续不变的容量。公开 XNU 的 `tcp_sbrcv_grow_rwin` 允许固定缓冲按 16 个 MSS 增长，`tcp_sbspace` 会调用该路径，不能将设置用户大小等同于禁止所有增长。该源码用于解释机制，本机行为仍用实际 socket 验证，不把公开源码版本等同于本机内核构建。

进一步的有界探针分别运行 128 连接、每连接 16 个 32 B 帧：默认已连接 MSS=16332，运行期间每连接都超过原 64 KiB 上限，峰值 277696 B；只限制 listener MSS 没有效果。接受后将 MSS 限至 1024 再重设缓冲，两个相应配置组的运行期间峰值均为 32768 B，未超原上限。这不是吞吐或物理内存结果，也不证明两次原服务失败的唯一原因。

## 决定与边界

- 仅 macOS 接受的连接先读取 TCP_MAXSEG，将其限制为当前正值与 1024 的较小值，再读取验证结果，然后设置原 16 KiB 收发缓冲。listener 不使用无效的 MSS 继承假设；Linux 沿用原缓冲配置，仍执行相同的运行期间上限检查。请求与回复都是原 32 B 帧，不改变业务负载、FIFO、状态或错误语义，不提高缓冲、预算或时限。
- 设置后以及每次 read/write 返回后读取实际收发缓冲，维护运行期间峰值；非法长度、非正值或超过 65536 B 明确拒绝，关闭当前连接并按既有规则继续处理剩余有界连接。缓冲拒绝和连接设置错误分别计数，失败时仍记录实际峰值，不以失败连接省略超额观测。MSS 的实际最大值在 macOS 报告，未限制该选项的平台用 null。
- `max_tcp_segment` 是配置确认时跨连接的最大 MSS，`max_socket_buffer` 是配置及各次 I/O 返回后的最大容量读数；二者均为明确采样点的观测，不是全时内核跟踪或物理分配峰值。
- 全部控制计数使用固定存储，不增加线程或重试。已发布请求或已提交状态不因后续 I/O/资源检查失败回滚。原 100 ms 绝对读写截止时间、50 ms 请求及等待、2 秒 accept 和 3 秒业务阶段保持。
- 检查范围从连接配置开始；接受前/握手中的内核缓冲可能已大于该上限，探针观察到过 326640 B。原适配器/连接预留仍是用户态保守逻辑额度，不是内核瞬时分配或 RSS 硬上限。未知内核变化仍可导致明确连接拒绝，不能据有限探针宣称任意系统/流量下的 OS 内存隔离或完整 VM 资源门禁通过。

## 验证

先用真实 loopback 单测在原实现复现运行期间超额，再检查新配置在 128 连接、每连接 16 帧、双向读写期间的 MSS 与收发缓冲；同时保留部分帧不能刷新读截止时间的回归。完整受限 AOT 增加原连接/帧数最大值 8×64 的真实请求/回复与最终状态回归，并检查新增错误计数和平台 MSS 字段，不扩大容量或放宽旧场景期望。

执行 workspace check、debug/release all-targets/doc-tests、完整原限 AOT、显式 BEAM 正确性、clippy、fmt、MSRV、依赖/unwind 与文档检查，以及可用 Linux 功能验证。旧失败与独立探针完整保留；成功复跑不撤销失败历史，也不关闭原生双平台、公平性、完整账本或 BEAM 吞吐/整机内存门禁。
