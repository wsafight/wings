# ADR-0093：等待前重查本 worker 的就绪队列

- 日期：2026-11-14
- 状态：已采纳（等待竞争修正，保留原启动退避）
- 依据：[ADR-0062](0062-sparse-ready-scheduler.md)、[ADR-0047](0047-cross-thread-ingress-requests.md)

## 问题与决定

Scheduler 每轮在 registry 锁内认领就绪项，随后出锁处理活栈，再次加锁决定是否以 Condvar 等待。旧决定只检查本轮是否执行过时间片；若第一次检查为空，另一个线程恰在两次加锁间入队并通知，worker 仍会等待至下一次通知或原一毫秒超时。通知不是业务计数，已经发布的就绪项不能依赖另一次通知才能被看见。此处是有界额外等待，不把它描述成无限死锁或全部超时根因。

在实际等待持有的同一 registry 锁内，重查本 worker 的 FIFO 队头：本轮没有认领工作且本 worker 已有就绪项时直接进入下一轮，不进入 Condvar。其他 worker 的就绪队列不能让本 worker 自旋。若本轮已执行时间片，仍直接继续原调度循环；关闭/本地活栈清理、每轮一个认领加一个时间片、固定归属与返回后迁移均保持。

已认领但 attach/start 因资源准入失败的路径保留原一毫秒有界退避，即使原消息已重排队也不能无进展忙重试。此次记录是否发生认领，不改变准入、重试消息/FIFO、配额、请求 deadline、quantum、预算、ABI v15 或业务语法。原等待时长不缩短、不延长；队列检查是常量时间，不扫描 actor 或额外分配存储。

## 验证与边界

先将原等待决定等价提取，再用同一锁内的确定序列复现：空认领、发布消息、通知、等待决定。旧决定在队头已存在时仍选择等待；修正后当前 worker 不等待、其他空队列 worker 仍等待，启动失败仍退避，执行过时间片不等待，队列只认领一次、最终账目清理。测试直接检查调度循环使用的决定，不以操作系统调度必须在某个微秒阈值内作为断言。

回复表另补正的非零 deadline 与实际 wait/发布/失败、取消竞争：使用已知单调截止时间及操作前后边界验证终态，跨越截止时允许合法竞争，不强求某个线程获胜。零 deadline 不能替代非零 Condvar 定时等待；迟到发布不得覆盖超时，早已选定回复不得被晚取消/超时改写，结果只消费一次、发布者结束后归还容量并可复用。可信 Rust fixture 不是生成代码的 safepoint 证据，真实 AOT/GC/失败与监督仍由完整入口验证。

运行 debug/release 全工作区、check/clippy/fmt/MSRV、完整受限 AOT 与可用 Linux 隔离验证；有界竞争重复保持原 CPU/墙钟限制，不重试失败业务。修正只消除已定位的等待窗口，不推出非零 deadline、长时公平性或尾延迟全面达标；原生双平台、完整业务值/账本及同负载 BEAM 性能/整机内存双门禁仍独立验收。

## 替代方案与重审

缩短超时仍保留竞争且增加空闲唤醒，延长请求期限则掩盖问题；两者均不采用。对所有就绪项立即重试会去掉准入失败退避，其他 worker 队列也不能由本 worker 消费。后续改变为可累计通知、work stealing 或 deadline 驱动 parking 时另立决策，重新验证关闭、唤醒与无进展资源重试。
