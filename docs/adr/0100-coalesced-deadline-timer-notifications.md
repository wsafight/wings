# ADR-0100：合并 deadline 计时器冗余通知

- 日期：2026-11-16
- 状态：实验后回退（2026-11-16 五对无稳定收益，未保留候选实现）
- 原拟部分替代：[ADR-0022](0022-worker-deadline-preemption.md) 的每次 arm/disarm 无条件通知策略；适用于 [ADR-0054](0054-bounded-multi-worker-scheduler.md) 的每 worker 计时器。当前仍沿原实现。

## 背景

前一轮宿主结果轮询优化保留了所有计时操作。Scheduler 每个时间片都 arm，返回再 disarm，旧计时器两次都通知 Condvar。短 handler 经常在 deadline 前结束，撤销后的线程没有需要立即执行的动作；无条件通知会制造额外调度和锁竞争。此前 profile 主要捕获等待状态，不足以量化该开销或证明它解释所有尾延迟。

## 候选方案（已回退）

在原计时控制锁内记录线程当前等待状态：Running、Idle 或实际 `wait_timeout` 的单调唤醒期限。它记录的是已进入/即将原子进入的等待，而不是上一次发布的业务期限。

- future arm 仍清除旧原子标志并更新当前业务 deadline；线程 Idle 时通知，等待一个更晚的实际唤醒期限时通知，线程 Running 或其唤醒不晚于新 deadline 时不通知。
- 已到期 arm 仍同步请求原子让出并清空当前 deadline，不等待计时线程；无需为这个空期限额外通知。
- disarm 在原锁内清空当前 deadline 并清除原子标志，但不通知。线程至多保留一次旧 timed wait，醒后重新检查当前 deadline；旧期限不能在撤销后请求让出。
- 线程进入 Condvar 等待前设置实际等待状态，返回并重新获得同一锁后设为 Running，再重读当前业务 deadline。虚假唤醒、已通知但尚未重新获锁，以及快速撤销/再次 arm 都按当前锁内值处理。
- stop 始终通知并 join，不能让关闭等待旧的长 deadline；归还原计费线程/控制租约的顺序不变。

不改变生成代码 safepoint、片预算、总预算、quantum、抢占标志的清除/请求规则、请求 timeout 或活栈线程归属。控制状态增加的固定字段仍在原 4096 字节余量内，保留 256 KiB 线程栈、原页预算及资源上限；不增加时钟线程、缓存或动态分配。ABI 继续 v15。

## 验证、风险与回退

确定性转移表检查 Idle、Running、早/相等/晚实际唤醒和撤销的通知决定；真实线程检查空闲 arm、已到期同步请求、长等待撤销后更早 rearm、延后不产生旧请求、观察计数守恒和长等待关闭 join。另用固定控制大小断言及既有三级准入、timer/worker/Scheduler AOT 回归验证资源和抢占。

原 CPU/墙钟/业务阶段不变，执行 debug/release 全部 harness、完整受限 AOT、check/clippy/fmt/MSRV。同业务前后比较固定使用 hot-queue 10000/s、30s 预热/60s 采样/五对交替；两版都保留 ADR-0099，唯一新增代码差异应为 timer。记录原始延迟、迟发、拒绝、超时及分口径内存，不从减少通知次数推导加速倍数。

最大风险是把当前业务期限误当作实际 timed wait，导致早 rearm 漏通知；因此二者分开记录且由同锁保护。回退只恢复 arm/disarm 的无条件通知和原控制状态，不改变业务协议/量子或放宽限额。共享计时服务、timer wheel、OS 亲和或改变抢占频率需独立决策。

实际证据见[计时通知优化验证](../validation-timer-optimization-2026-11-16.md)。CPU 硬配额、原生 Linux 和 BEAM 双目标门禁仍未完成。

## 实验结论

功能回归通过不代表值得保留。原 hot-queue 10000/s 五对采样中，候选共 1240 次超时、41747 次队满，原版无超时、2485 次队满；候选 p99 仅两对较低、p999 仅一对较低。虽有环境/迟发波动，现有证据不支持稳定收益，故撤销 timer.rs 候选和仅服务于候选状态的测试，保留既有 timer/抢占回归、原始实验与冻结的候选源码。ADR-0099 不变，不为此调整量子、资源、业务或截止时间。
