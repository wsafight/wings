# 产品定位

[文档目录](../docs.md) · [项目概览](../README.md)

## 一句话定位

Wings 是微进程虚拟机，目标是比 BEAM 更快、更省内存，同时保留消息传递、公平调度和监督恢复的编程模型。

## 为什么做这个

大量小状态会话需要轻量进程，也要控制消息处理开销和内存占用。Wings 以 BEAM 为比较对象，关注两点：

- **更快**：在相同 CPU 配额和尾延迟要求下，提高业务 handler 与消息处理的持续吞吐。
- **更省内存**：在相同业务状态、mailbox 和活跃比例下，减少进程元数据、堆容量和执行栈的总开销。

两项目标都要在同一组代表性负载下验证，条件见[评测与验收](evaluation.md)。AOT、状态布局和分配策略能带来多少收益，需要实测。

| 方案 | 执行方式 | 故障与资源边界 | 需要测量的成本 |
|---|---|---|---|
| [kameo](https://docs.rs/kameo/) / 普通 Rust actor | Rust 原生代码 | 可处理部分 panic；不自动约束任意原生代码、CPU 和内存使用 | task/actor 状态、消息队列、库与业务自建的配额机制 |
| WASM actor / [Wasmtime](https://wasmtime.dev/) | 后端可采用 JIT 或预编译 | 线性内存与 trap 隔离受管代码；host imports 属于可信边界 | 实例元数据、栈、线性内存实际驻留、地址预留，以及 host call |
| [BEAM](https://www.erlang.org/doc/system/eff_guide_processes.html) | 字节码执行，支持 JIT | 受管进程堆与调度；任意不安全 NIF 仍可能影响宿主 | 普通/冬眠进程、活数据、mailbox、off-heap binary 和调度成本 |
| Wings | 拟定的受管 AOT | 受限语言 + 强制插桩 + 多级资源额度；可信原生错误仍影响整个 VM 进程 | 同状态和语义下的整机内存、吞吐、尾延迟，以及新工具链成本 |

BEAM 是主要基线；kameo/Tokio 用于观察原生执行成本，Wasmtime 用于比较另一种受管执行方案。不同故障与资源边界的结果分开报告。

## 目标用户与场景

首先面向团队自行开发、能接受新语言的会话系统，不用于运行敌对代码的插件平台：

1. **IM/IoT 会话层**：大量小状态、低活跃比例的进程。VM 通过有预算的原生 I/O 内建管理连接与编解码，受管 handler 负责状态逻辑；连接缓冲区仍纳入整机账本。
2. **Agent 编排**：长生命周期状态、异步工具调用、超时和取消。外部工具与 native 扩展不能借此获得同进程沙箱保障。
3. **软实时游戏/仿真逻辑**：房间和实体适合消息模型，但要验证最慢 handler 与 runtime 长操作，不能承诺每 tick 的硬截止时间。
4. **可信团队维护的规则/handler**：统一工具链和部署来源，主要防业务错误与额度滥用。敌对租户提交代码和第三方原生插件不属于首版范围。

不做：硬实时、安全对抗型沙箱、任意 Rust 库透明复用、浏览器和首版分布式。

## 选型对照

- **业务可控，只需要任务重启**：先考虑 kameo 或 Tokio，判断现有库与业务限流是否够用。
- **运行不可信第三方代码**：选择成熟 WASM 方案或加固后的 OS 隔离。Wings 的子进程池尚未交付，线程池也不能代替进程隔离。
- **复用 Rust crypto/编解码库**：由 VM 的可信原生内建封装，通过有预算的受管接口访问。这层接口不会自动保证库内部的可抢占性和故障隔离。
- **需要成熟 OTP 与现有 Elixir/Erlang 生态**：继续使用 BEAM。Wings 只对声明的语义子集做参考测试，不复刻整个生态。

Wings 适合需要承载大量小状态 actor、重视吞吐和内存的应用，前提是团队能接受 `wings-lang` 的语义与迁移成本。

## 实现取舍

1. **AOT 执行**：受限前端与现成编译后端用于优化 handler 执行路径；根维护、资源检查和消息编解码的成本一并计入。
2. **按活跃度分配内存**：handler 返回后释放执行栈，可选冬眠再压紧业务状态；同时测量普通 Idle 与冬眠，保留唤醒和编码成本。
3. **统一受管边界**：语言、编译器和 runtime 共同约束内存访问、调度与资源准入。语言没有 unsafe 语法，仍不能保证编译器和 runtime 的实现安全。
4. **可回收的进程资源**：不执行任意用户对象析构，批量回收堆块；退出 fan-out、外部资源和回收时间继续计费，不承诺 O(1)。
5. **公开语义差异**：无 actor 内同步等待、有限 mailbox 和显式发送错误；热更新只在静止边界迁移，首版不含分布式与原生插件池。

首版只维护一个前端，使用显式根链和现成机器码后端，减少工具链的开发范围。macOS AArch64 与 Linux x86-64 共用受管契约，平台层分别验证；优化方案见[激进优化](optimizations.md)。

## 采用路径

从小 handler 开始，逐步验证：

1. 编译运行一个无外部副作用的小 handler，验证状态表示、消息协议和工具链成本。
2. 加入额度、异步 request、超时与取消，验证错误和背压路径。
3. 加入监督恢复与诊断后再试点。故障隔离由受管执行机制提供，监督负责恢复。
4. 冬眠或热更新有实际收益时再启用或评估，上线不以这两项为前提。

消息与 handler 的编程方式相近，但现有 Rust actor 仍需改写。受限语言、异步交互和消息 schema 都有学习与迁移成本。

## 产品验证节点

- **M0 后**：在 macOS AArch64 与 Linux x86-64 分别固定 BEAM 版本、配置与负载，建立吞吐、尾延迟和整机内存基线；用现有方案复现死循环、消息/spawn 洪泛和本地配额耗尽，区分资源契约。原生崩溃仅在隔离的测试 OS 进程中演示，不作为同进程隔离优势。
- **M2 后**：发布相对 BEAM 的吞吐、尾延迟与活跃进程内存数据，附 kameo/Tokio 和 Wasmtime 辅助对照。只在 tiny state 或单一指标上领先，不算达标。
- **M3 后**：补齐普通 Idle、冬眠和不同活跃比例的内存曲线，并比较唤醒与 GC 成本。
- **M4 后**：找一个会话层或 Agent 编排试点，评估开发成本、诊断成本和真实恢复数据。试点前要具备生产诊断能力。
- **M5 及以后**：热更新、原生子进程池、额外平台组合和分布式分别评估是否立项，时间表不代表一定开发。

## 成功标准（18 个月）

- 在预先确定的代表性负载中，同时取得高于 BEAM 的持续吞吐和低于 BEAM 的整机 RSS，满足相同尾延迟要求；普通 Idle、活跃和冬眠场景分别报告，不拼接最优值。
- 在至少一个真实目标负载中复现上述性能与内存收益，并评估语言迁移、诊断和故障恢复成本。
- 单机百万微进程作为容量实验目标，必须公开 state、mailbox、活跃比例、VM 连接成本、硬件和资源上限，不能等价为百万进程同时执行。
- 抢占、GC、唤醒与恢复按[评测与验收](evaluation.md)中的条件测量；未达标先分析成本，不能通过取消强制抢占保留性能数字。
- 至少一个非项目维护者的试点或生产部署，且能复现配额、取消、监督和诊断行为。18 个月是决策窗口，不是全部可选功能的交付承诺。
